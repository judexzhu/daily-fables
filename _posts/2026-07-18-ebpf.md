<section class="zh" markdown="1">
在一座终年不打烊的大港口里,货轮日夜进出,潮汐从不等人。港务长立下一条铁律:任何维修都不能让港口停摆哪怕一分钟——闸门不能拆,航道不能封,连值班室的钟都不许停。

可港务长又常常需要在某个闸口"顺便看一眼"——比如数一数今天有多少艘挂着某国旗的船经过,或者在某种可疑货物经过时记一笔。传统做法是把闸口整个拆下来重建,加装新的机关,但那意味着停工数周,港务长绝不答应。

于是港口设了一位哨站文员的岗位。任何人想在闸口"顺便看一眼",都得先写一张便条,交给一位极其苛刻的老稽查员过目。这位稽查员从不放行含糊其辞的便条:便条里不准写"绕着圈子等着"这种话,必须在读完一遍货单前写完,也不准伸手去翻不属于自己的抽屉。只有条理清楚、保证会读完就停笔的便条,才会被盖章批准,贴在闸口的哨墙上。

便条一旦贴上,就不再需要稽查员盯着——它会随着每一艘船经过闸口时被自动念一遍,速度快得像是刻进了闸门的齿轮里,而不是每次都要翻出来重新读一遍手写体。念便条的人不会记院子里所有的事,只会往墙角挂着的一本公用记事本里记一笔它被交代要记的东西——比如"今天第37艘挂红旗的船"。这本记事本随时可以被港务长翻阅,却不会被哨站文员私自撕页或篡改。

最妙的是,如果某天港务长想撤掉这张便条、换一张新的,只需要把旧便条摘下来,贴上新的,闸门本身、航道、整个港口结构完全不用动一根钉子。

——到这儿你大概已经认出来了:这就是 *eBPF*。

**概念解析**:eBPF(extended Berkeley Packet Filter)允许用户态程序把一小段沙盒化*字节码*动态挂载到 Linux 内核的特定钩子点(*hook*,如网络收发包、系统调用、内核函数入口)上执行,而不需要重新编译内核或加载传统内核模块。挂载前,内核里的 *verifier* 会静态检查这段程序:禁止无限循环、必须在有限步数内终止、不能越界访问内存——通过验证的程序会被 *JIT 编译*成机器码,以接近原生的速度在钩子点触发时运行。程序通过 *eBPF map*(键值存储)与用户态或其他 eBPF 程序共享状态,比如计数器、连接跟踪表。这正是 Cilium、Falco、bpftrace 等云原生可观测性与网络工具的底层机制——OpenShift 上跑的 CNI(如 OVN-Kubernetes 的部分加速数据路径)也依赖它,在不停机、不改内核源码的前提下给数据面装上可编程的"哨站"。

_隐喻对应表_

- 港口 → Linux 内核(不能停机的运行系统)
- 闸口 → hook point(网络收发包、系统调用等挂载点)
- 便条 → eBPF 字节码程序
- 老稽查员 → verifier(静态验证器,拒绝死循环与越界访问)
- 便条被刻进齿轮、快速念出 → JIT 编译为机器码
- 公用记事本 → eBPF map(用户态与内核态共享的键值存储)
- 换便条不用动闸门 → 动态加载/卸载 eBPF 程序,无需重新编译内核或重启

<section class="en" markdown="1">
In a harbor that never closes, ships come and go around the clock, and the tide waits for no one. The harbormaster has one inviolable rule: no maintenance may ever stop the harbor, not even for a minute. Gates cannot be dismantled, channels cannot be closed, and the clock in the watch-house never stops ticking.

But the harbormaster often needs to "just take a quick look" at a gate — count how many ships flying a certain flag pass today, or flag a certain kind of cargo when it goes by. The old way was to tear the gate down and rebuild it with new machinery, which meant weeks of shutdown the harbormaster would never allow.

So the harbor created a post: the sentry clerk. Anyone who wants to watch a gate must first write a note and hand it to a famously strict old inspector. This inspector never approves a vague note. The note may not say "wait in a loop" — no unbounded loops. It must finish reading before the inspector reaches the end of the day's manifest — a bounded number of steps. And it may not reach into drawers that aren't its own — no out-of-bounds memory access. Only a note that is orderly and provably terminating gets stamped and pinned to the sentry wall at the gate.

Once pinned, the note no longer needs the inspector watching over it. It gets read automatically every time a ship passes the gate, at a speed as if it had been carved directly into the gate's gears — not re-read from handwriting each time. Whoever reads the note doesn't remember everything happening in the yard; it only jots down, in a shared logbook hanging on the wall, exactly what it was told to record — "37th red-flag ship today," say. That logbook can be checked by the harbormaster at any time, but the sentry clerk cannot tear out its pages or forge entries.

Best of all, if the harbormaster wants to retire a note and pin up a new one, all it takes is unpinning the old and pinning the new. The gate itself, the channel, the whole structure of the harbor — not a single nail needs to move.

— By now you've probably recognized it: this is *eBPF*.

**What it is**: eBPF (extended Berkeley Packet Filter) lets a userspace program dynamically attach a small piece of sandboxed *bytecode* to specific *hook points* in the Linux kernel — packet ingress/egress, syscalls, kernel function entry points — without recompiling the kernel or loading a traditional kernel module. Before attaching, the kernel's *verifier* statically checks the program: no unbounded loops, must terminate within a bounded number of steps, no out-of-bounds memory access. A program that passes gets *JIT-compiled* into native machine code, so it runs at near-native speed each time the hook fires. Programs share state with userspace or other eBPF programs through *eBPF maps* — key-value stores used for counters, connection-tracking tables, and more. This is the mechanism underneath Cilium, Falco, and bpftrace, and much of modern cloud-native networking and observability — the CNI paths OpenShift clusters rely on (parts of OVN-Kubernetes's accelerated datapath, for instance) use it to attach programmable "sentries" to the data plane without downtime or kernel source changes.

_Metaphor mapping_

- The harbor → the Linux kernel (a system that can never stop running)
- The gate → a hook point (packet path, syscall, kernel function entry)
- The note → an eBPF bytecode program
- The old inspector → the verifier (rejects unbounded loops and out-of-bounds access)
- The note carved into the gears, read at speed → JIT compilation into native machine code
- The shared logbook → an eBPF map (key-value store shared between kernel and userspace)
- Swapping the note without touching the gate → dynamically loading/unloading eBPF programs, no kernel rebuild or reboot
</section>
